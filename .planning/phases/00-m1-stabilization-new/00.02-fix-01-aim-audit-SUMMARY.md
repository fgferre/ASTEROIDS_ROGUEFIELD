## In-Plan Fixes Applied

None — audit-clean. The hypothesized `targetingUpgradeLevel`-advancement bug
from the plan's `<interfaces>` block dissolved on inspection of
`src/modules/UpgradeSystem.js:803-810`, where `applyUpgradeEffects` injects
`{ upgradeId, level: newLevel, category }` into every upgrade event payload
before emission. `CombatSystem.applyAimingUpgrade` (lines 884-890) correctly
consumes the injected `level` and advances `this.targetingUpgradeLevel`
accordingly. The handler-side gating chain (`>= 1 → dangerScoreEnabled`,
`>= 2 → dynamicPredictionEnabled`, `>= 3 → multiLockTargets / cooldown`)
is intact in production.

The regression suite ships per REVIEWS Concern 8 to lock this correct
behavior against future regressions.

## Concern 4 Moving-Target Angle Diff (Observed)

The Concern-4 test (targeting_suite rank 2, predictive vs. linear aim against
a moving target) was engineered so the natural quadratic-intercept time
(~1.20 s) lies outside the linear-prediction clamp [0.1, 0.6] s but inside the
dynamic-prediction clamp [0.05, 1.0] s. The two paths therefore clamp to
different times (0.6 s vs. 1.0 s) and yield different aim points.

- **Player position:** (400, 300)
- **Enemy position:** (700, 400) (distance ≈ 316, in `COMBAT_TARGETING_RANGE = 400`)
- **Enemy velocity:** (300, -100)
- **`BULLET_SPEED`:** 550
- **Observed `firstAngle` rank 1:** non-null (linear-clamped, 0.6 s lead)
- **Observed `firstAngle` rank 2:** non-null (dynamic-clamped, 1.0 s lead)
- **Observed angle diff:** ≈ **0.0831 rad** (≈ 4.76°)
- **Floor required by D-04 / Concern 4:** 0.01 rad
- **Margin:** 8.3× above floor

The state-flag fallback (`dynamicPredictionEnabled === true`) is included as a
secondary sanity assertion in the same test case, NOT as a substitute for the
angle diff (per REVIEWS Concern 4 explicit ban).

## Decisions Made

1. **Outcome = audit-clean → Task 2 NO-OP.** Skipped source-edit branch
   entirely. Audit doc's `## Disposition summary` carries the required literal
   "No in-plan fixes required (audit-clean)" phrase.
2. **GamePools must be initialized in `beforeAll`.** Without this,
   `CombatSystem.createBullet` line 1849 throws `Cannot read properties of null
   (reading 'acquire')`. Pattern borrowed from
   `tests/integration/determinism/start-reset-cycle.test.js`.
3. **Concern 4 test setup engineered for clamp divergence.** Initial setup with
   default position/velocity produced an angle diff of 0 because both the
   linear and dynamic predictors agreed on the natural intercept time. Moved
   the enemy to (700, 400) with velocity (300, -100) so the natural time
   (~1.2 s) lands outside the linear clamp's 0.6 s upper bound — forcing the
   two predictors to land on different times.
4. **Rank-3 assertion uses vector-multiset-diff + `targetingUpgradeLevel`
   advancement, NOT `multiLockTargets` delta.** The `multiLockTargets` field
   initializes to `baseTargetCount = 4` from `COMBAT_AIMING_UPGRADE_CONFIG`
   (gameplay.js:216) regardless of rank, so it's not a rank-progression
   marker. The actual rank-3 contract is that `targetingUpgradeLevel >= 3`
   triggers `usingAdvancedBattery` in `handleShooting` line 487, which routes
   through `buildLockAssignments` to fire at distinct lock targets.
5. **Test-emitted payloads include `level` field explicitly.** Per audit
   Finding 1, this matches the production behavior (UpgradeSystem injects
   `level`), so bare-catalog-payload emission in tests would silently fail to
   exercise the rank-progression path. Documented in the test file header.
