# Aim System Audit — 2026-05-12

Phase 0 (M1 Stabilization, FIX-01). Audit-first per D-03. Category split per REVIEWS Concern 3.

**Method:** One row per `(upgradeId, rank)` for every upgrade in
`src/data/upgrades/offense.js`. Audit is split into two categories with
DIFFERENT expectation bars:

- **Vector-Affecting:** `multishot`, `targeting_suite`. Each rank MUST produce
  an observable change in projectile vectors (count, angle, spread, or aim
  point against a moving target). A "Y" requires direct evidence of this on
  the next fired projectile set OR (for targeting_suite rank 2 specifically)
  a measurable angle diff against a moving target vs. the rank-1 baseline.
- **Vector-Neutral:** `plasma`. Each rank MUST change a damage value AND
  MUST NOT change the projectile vector set vs. the no-upgrade baseline.
  A "Y" requires BOTH conditions.

## Scope

- Aim-related upgrades: plasma (damage scalar, VECTOR-NEUTRAL),
  multishot (projectile count, VECTOR-AFFECTING), targeting_suite (prediction
  + multi-lock, VECTOR-AFFECTING).
- Out of scope: visuals (`upgrade-thruster-visual` etc.), mobility, defense,
  HUD-only effects.

## Cross-category sources verified during audit

- `src/data/upgrades/index.js` aggregates `OFFENSE_UPGRADES`, `DEFENSE_UPGRADES`,
  `MOBILITY_UPGRADES`, `UTILITY_UPGRADES`. Of these, only `OFFENSE_UPGRADES` is in
  scope per the phase context (D-03). The other catalogs were spot-checked: no
  defense / mobility / utility upgrade currently emits an aim-affecting event
  (no `upgrade-multishot`, `upgrade-aiming-suite`, or `upgrade-damage-boost`
  outside `offense.js`). Audit scope is the three offense.js entries below.
- `src/modules/UpgradeSystem.js:803-810` (the production effect emitter) injects
  `{ upgradeId, level: newLevel, category }` into every upgrade event payload
  ON TOP of the catalog's `effect.payload` object. This means handlers that
  branch on `data.level` (notably `CombatSystem.applyAimingUpgrade` lines 884-890)
  see the injected level field in production. Tests that emit bare catalog
  payloads MUST include `level` themselves to reproduce the production
  rank-progression semantics — see `## Findings` below.

## Findings

All nine rows (6 vector-affecting + 3 vector-neutral) audit as `Y` in production behavior.
No bugs were found that match Plan 02's in-plan fix dispositions (CombatSystem.js or
offense.js edits). The following observations were made but are not bugs:

### Observation 1 — `targetingUpgradeLevel` advancement depends on production payload injection (not a bug)

`CombatSystem.applyAimingUpgrade` (line 884-890) reads `data.level` and only advances
`this.targetingUpgradeLevel` when `Number.isFinite(data.level)`. The `offense.js` catalog
payloads for `targeting_suite` ranks 2 and 3 do NOT include a `level` field — they only
carry `{ dynamicPrediction: ... }` or `{ multiLockTargets: ..., cooldownMultiplier: ... }`.

This initially looked like the suspected bug from the plan's `<interfaces>` block. On
inspection of `src/modules/UpgradeSystem.js:803-810`, the `applyUpgradeEffects` function
explicitly injects `{ upgradeId, level: newLevel, category }` into every upgrade event
payload BEFORE emitting. So the production emission always carries `level`, and
`applyAimingUpgrade` correctly advances. The handler-side state-progression chain
(`targetingUpgradeLevel >= 1 → dangerScoreEnabled = true`; `>= 2 → dynamicPredictionEnabled = true`;
`>= 3 → multiLockTargets / cooldown`) is intact.

**Disposition:** Not a bug. Production behavior is correct. The audit row stays `Y`.

**Test contract consequence:** Any test that emits `upgrade-aiming-suite` events MUST
include a `level` field in the bare payload (e.g., `eventBus.emit('upgrade-aiming-suite',
{ level: 2, dynamicPrediction: { ... } })`) — emitting the catalog `effect.payload`
verbatim WITHOUT the UpgradeSystem-injected `level` is a test-harness configuration error,
not a CombatSystem bug. The regression test in Task 3 includes the injected `level` field
to faithfully reproduce the production emission.

### Observation 2 — multiLockTargets prerequisite enforced at catalog level (not a handler concern)

`offense.js` line 207-214 declares `targeting_suite` rank 3 has a `prerequisites: [{ type: 'upgrade', id: 'multishot', level: 1 }]` clause. The runtime prerequisite check
lives in the UpgradeSystem (eligibility gating, not in `applyAimingUpgrade`). Once rank 3
applies, `applyAimingUpgrade` correctly sets `multiLockTargets = 4`; the rank-3 fire-loop
in `handleShooting` line 530-606 then iterates `totalShots` and reads multiple distinct
lock assignments via `usingAdvancedBattery`. The interaction with `multishot >= 1` is
correct: `computeLockCount` line 1110 returns `Math.min(targetCap, shotCount)`, so a
player with rank-3 targeting + rank-1 multishot (the minimum legal config) gets 2 locks
(not 4), and a player at max multishot gets the full 4. This is the catalog's intended
balance, not a bug.

**Disposition:** Not a bug. Audit row stays `Y`.

### Observation 3 — Plasma damage is `Math.floor`-truncated each rank (not a bug, design choice)

`PlayerSystem.js:347` applies `this.damage = Math.floor(this.damage * data.multiplier)`.
For starting damage = 10 and the cumulative ranks (×1.25 → ×1.20 → ×1.15), the final
damage is `Math.floor(Math.floor(Math.floor(10 * 1.25) * 1.20) * 1.15) = Math.floor(Math.floor(12 * 1.20) * 1.15) = Math.floor(Math.floor(14) * 1.15) = Math.floor(14 * 1.15) = 16`,
which is slightly less than the naive `10 * 1.25 * 1.20 * 1.15 = 17.25` (truncated to 17).
The catalog text describes the upgrade as "+70% total damage" — within the float-truncation
band, this is a stated rounding behavior, not a bug. The regression test asserts
**monotonic damage increase** (rank 1 < rank 2 < rank 3) rather than the exact multiplier,
which is the contract D-04 actually requires.

**Disposition:** Not a bug. Audit row stays `Y`.
